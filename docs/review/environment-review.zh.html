A · PROPOSAL REVIEW

这个环境值得做，
而且方案可落地吗？

看业务价值、工作流、数据计划、依赖、投入与可审查的验收计划。此时可以有待定事项，但要说明如何解决。

是否真的运行正确？

验收：验证通过并合并后，才算已接受的贡献。

逐项对照批准的交付内容

评审边界先说清

业务规则由 App 实现；场景和平台能力分别核对。

APP

可复用业务能力

记录格式、查询与写入、业务状态转移、接收事件、收发契约、素材与本地测试。

TASK

特定用户与场景

用户账户与历史、目标与偏好、事件内容和时间安排、用户回应、评分标准。

CORE / INFRA

运行与接入保障

装载数据、可信身份和权限、模拟时间、提交与回执、消息投递及平台验证。

本次用什么作依据？

现行主仓库的提案模板与贡献流程；PR #12 的公开 Core / Messaging、App 说明与不变的 Mail / Calendar 契约；四份 Environment 提案的固定提交。

PR #12 仍是公开参考方案。它尚未合并，不应把它的所有实现限制直接当作永久平台规则。接口差异需要讨论适配或平台扩展。

这份材料提供评审建议，不表示已经发出 GitHub review、批准提案或完成实现验收。

四个案例，校准四种判断

先统一判断方法，不先设一个总分。核心业务缺口、平台依赖、表述待明确和可选范围，应分别记录。提案阶段不要求成品代码；Task 的模型数量和难度门槛，不直接作为 Environment 的验收门槛。
02 / PROPOSAL REVIEW

看方案，而不只是填表。八个维度，回答三个问题。

它有什么用？能否按计划交付？交付后如何判断做对了？每项都需要“依据 + 理由 + 修改要求”，而不是只打一个勾。

怎么区分问题的性质

必须先解决的设计缺口

核心流程无法完成、关键数据不可用、权限边界违背需求，或硬依赖没有可行承接方案。需要改设计或缩小范围。

需要澄清或平台确认

时间边界、重试方式、接口命名、资源预算与依赖版本。先写明确问题和负责人，不立即把它定成 App 的 bug。

不阻塞首版的可选项

不在批准范围内的更多产品功能、未来渠道或装饰性 UI。记录即可，避免评审范围无止境扩大。

让验收计划变成可执行的例子

以“课程试用到期”为例，至少说清楚下列链条。

还要补：输入、相关记录、失败时哪些状态不变、由谁提供时钟与权限。最终工具字段可在设计批准后细化。

提案审核的是这条验收路径是否合理；实现审核才要求运行结果证明它成立。

本次不建议继续扩大提案模板

当前模板已经覆盖操作入口、状态生命周期、事件、共享数据，以及建设、数据素材、集成、验证、依赖和工作量。先用这些字段审查内容是否足够，具体 SDK、鉴权与日志存储交给平台；不要让贡献者再填写一份内部部署设计。

03 / REVIEW CALIBRATION

对着真实提案提问题。指出差距，也给出能执行的改法。

四份案例均处于提案阶段。下面分析的是文档承诺和接入前提，不能据此认定尚未提交的实现有 bug。作者已经提出的开放问题也会明确标出。

这些结论的适用范围只覆盖下面链接中的四份提案与已核对版本，不代表对全部 Environment PR 的审查。PR #12 的资源限制、接口和消息通道是当前参考实现边界；新 App 可以提出扩展，但必须说明依赖和验收方法。

能本地测试，也要证明能接入平台。

公开 App 怎么自己测？

PR #12 示例使用 Node.js 18+，无需外部依赖。Mail 和 Calendar 分别运行：

cd examples/apps/mail
npm test
npm run example

# Calendar 使用自己的目录运行相同命令

测试实际调用 App 的业务函数；example 应用一个事件并显示前后数据。这是独立业务层证据；下方公开运行套件进一步验证真实 MCP 与持久化。

平台接入看什么证据？

  • 提交 SHA、批准范围、App 与公开 runtime 版本。
  • 实际 MCP 输入、返回值、提交后的状态与版本。
  • Agent 管理调用被拒绝，Infra 合法装载成功。
  • 如声明跨 App 收发，核对目标 App 状态与投递回执。
  • 每个失败路径及重试都有可复现结果。
平台还不能运行时，标“未测试”。不能把本地 mock 通过写成平台已通过，也不能把未交付的平台依赖记作贡献者的实现失败。

完整公开验证：从同一份仓库运行

Node.js 18+，不需要私有 Core、平台密钥或模型 API。App 自带业务测试，公开 runtime 提供真实 MCP 与状态验证。

# 仓库根目录：完整参考验证

# 检查一个实际提交包（也可换成 apps/<app-id>）

谁验证什么

作者先跑业务测试与公开 runtime；reviewer 固定 App 和 runtime 提交再复测。App-only PR 的 CI 从 base 版本加载验证器，避免仅靠提交包自己的测试宣布通过。

首次引入 runtime 时，base 还没有验证器，该项明确记为“未运行”，需要维护者审查。人工业务／素材审核、正式平台部署验证仍单独记录。

跨 App：先读接收契约，再实现自己的发送端

接收 App

拥有自己的记录与业务
→
发送 App
按该契约构造消息
声明 publishes
→
Infra / Messaging
可信账户绑定与授权

不要在订单 App 里重写一个邮箱，也不要直接改接收方的状态文件。只发、只收、双向、无消息能力均合法；App 的业务工具调用与消息投递分别接入。

Mail 是例子，不是唯一接收端。验证包括独立订单通知 → Mail、Mail → Mail，以及测试用 Noticebox 自定义渠道的真实投递。Noticebox 只证明通用桥接，不代表完整 Messages / Push 产品。Calendar 保持空收发声明，单独验证业务与 calendar.upsert。

跨 App 接入指南（PR12 分支） · 公开运行套件

历史数据：Infra 装载，Agent 使用

Task 决定装入什么历史；App 定义合法格式；Core / Infra 执行装载和权限检查。

Task 提供场景数据账户、历史邮件 / 日历、素材与引用。以 App 的 seed schema 为准。
→
Infra 管理入口env.load_seed 装载基线；env.apply_event 应用运行中变化。
→
隔离的 App 状态App 校验业务；Core 校验并提交。Agent 通过获授权的业务工具读取 / 操作。
验收用例：装入昨天的 3 封邮件，再追加今天的 1 封。Infra 装载后，Agent 只能在授权范围看到记录；它猜中 env.load_seed、env.reset 或注入工具名也不能执行。追加事件只产生一次效果，另一个 run 不出现这些记录。远程部署还需验证实际身份与网络入口，不能仅靠工具列表隐藏。

交付包里，哪些文件证明什么？

同一个 App 包用于作者本地验证与后台接入，测试证据各有边界。

文件 / 目录作者交付的内容reviewer 核对什么
app.json
package.json		版本、入口、文件引用、本地运行命令依赖清楚；路径有效；按说明可以运行。
tools.json
plugin.cjs / src/		输入输出、读写效果与真实业务实现实际返回和状态变化符合声明；错误路径正确。
schemas/
fixtures/		数据、状态和事件格式；最小历史与样例记录数据符合 schema 与业务约束；可替换为 Task 数据。
contribution/能力、依赖、收发方向、GUI、素材目录与来源声明对应已实现能力；源数据、媒体与许可可核查。
tests/
examples/		本地业务测试、合法调用 / 事件和预期结果成功与失败都覆盖；能复现；平台结果没有被伪造。
assets/ / gui/承诺的素材字节和可选业务界面可读取、共享同一状态；GUI 是否真的可供 Agent 操作。
src/diagnostics.cjs可选步骤日志适配有 / 无 hook 不改变业务；不记录内容和密钥；最终提交由 host 判定。

业务返回与步骤日志是两条通道

Agent 调用业务 MCP
→
Core 检查身份、权限、输入
→
App 业务返回 data + result
→
Core 提交校验、持久化、版本
→
MCP 返回Agent 观察到业务结果
App 关键步骤 → 可选 ctx.log → Core 关联调用与最终结果 → 独立诊断文件 → Infra / 维护者查看

当前约定：PR #12 的日志 hook 是可选扩展；App 不依赖它完成业务。已承诺诊断能力时，检查失败步骤、重试、调用关联与结果一致性。

明确边界：prepared 不等于 committed。日志不进入 Agent 返回；集中收集、保留时间、远程访问、告警由部署层提供。

当前参考能力，不能越界推断Mail 收发示例是文本 Email；Calendar 尚未声明跨 App 消息收发，但支持 Infra 更新事件。参考资源实现未包含 PDF / SVG；通用 MIME 字段可表达一种格式，不等于运行时支持它。GUI renderer 或 reviewer 管理页面也不自动等于完整 Agent CUA 环境。

下一步怎么执行

建议分工方式，会上确认；不改变仓库现有批准与合并流程。

01 · 初评

固定范围和版本

主 reviewer 读完整提案、关联任务与已有评论；区分事实、待确认项和推荐修改。

02 · 复核

用同一个案例校准

第二位 reviewer 复核关键结论；平台负责人确认硬依赖，避免不同 reviewer 重复扩大范围。

03 · 回到 PR

记录可执行结论

由 maintainer 记录批准范围与 commit；实现时逐项提交证据，重大变更重新审设计。

评审记录草稿

填入依据和建议，复制或下载后人工确认。

不会自动提交 GitHub

记录保存在本机浏览器；没有网络上传。不要在此填写凭据或个人数据。
